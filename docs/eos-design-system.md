## 规范优先级与强制执行

1. 用户当前明确要求优先于本文件；本文件优先于已测量的外部设计意图；两者都优先于旧代码和旧截图。
2. 新增或重构组件必须先读取本文件，再对照外部设计参考的组件实例、变体、状态和尺寸。
3. 组件代码只能引用语义令牌，不得在组件 CSS 中自行发明颜色、圆角、阴影或间距。
4. Light 和 Dark 必须同时实现并验证，不能只实现一套主题。
5. 图标和图片必须使用 Figma 对应的真实资源或项目中已确认一致的资源，不能用近似占位图标。
6. 布局使用内容关系和可伸缩布局实现，不用只为匹配截图的绝对坐标。
7. 每个组件实现后必须进行结构检查和 Light/Dark 截图核对。

## 字体与排版

- 默认字体：`Inter`
- Regular：正文、说明、占位文本
- Medium：标签、按钮、标题、强调文本
- 字重：Regular `400`，Medium `500`
- 字间距默认：`0px`

| 令牌 | 字号 | 行高 | 用途 |

| `text-xs` | 12px | 16px / 20px | 辅助说明、元信息、分隔文字 |
| `text-sm` | 14px | 20px / 24px | 正文、标签、按钮、输入内容 |
| `text-base` | 16px | 24px | 主要正文、标题 |
| `text-lg` | 18px | 28px | 较大标题 |
| `text-xl` 至 `text-9xl` | 20 / 24 / 30 / 36 / 48 / 60 / 72 / 96 / 128px | 对应 Tailwind leading | 页面标题和展示型内容 |

## 间距令牌

Figma 基础集合中的间距值包括：

`0, 1, 2, 4, 6, 8, 10, 12, 14, 16, 20, 24, 28, 32, 36, 40, 44, 48, 52, 56, 60, 64, 72, 80, 96, 112, 128, 144, 160, 176, 192, 208, 224, 240, 256, 288, 320, 384px`

- 2px：微调、分隔点

- 16px：内边距、常规组件间距
- 20px：区域间距

- 48px：大区域间距

## 阴影与表面

Figma 中常见的控件阴影组合为：

```css
0 2px 4px var(--field-shadow, rgba(0, 0, 0, 0.04)),
0 1px 2px var(--field-shadow-2, rgba(0, 0, 0, 0.06)),
0 0 1px var(--field-shadow-2, rgba(0, 0, 0, 0.06))
```

输入框使用略轻的组合：

```css
0 2px 2px rgba(0, 0, 0, 0.04),
0 1px 1px rgba(0, 0, 0, 0.06),
0 0 0.5px rgba(0, 0, 0, 0.06)
```

表面默认支持 `backdrop-blur`，当前 Kit 变量 `blur = 0px`、`depth = 0px`；不要自行增加玻璃效果。

## 极致界面工程规范

### 颜色与主题

- 颜色分三层：基础色阶、语义令牌、组件令牌。组件只能消费语义或组件令牌，不能直接消费色阶。
- 每个色阶必须有实际角色；不为没有使用场景的色阶增加维护成本。
- 主题只使用一种切换机制。EOS 使用宿主或祖先节点的 `data-eos-theme="light|dark"`，不得为同一组令牌叠加媒体查询或另一套 `.dark` 机制。
- 每个颜色只承担一个语义。主色表示主要交互；危险、成功和警告必须保持可区分。
- 一个视图中只有一个主要填充动作；多个彩色填充仅用于表达不同状态或分类。
- 颜色不能作为唯一状态信息，必须同时提供文字、图标、边框、形状或结构差异。
- 所有实际渲染的前景色/背景色组合必须计算对比度；未测量的值不得写入验收结论。
- 颜色对比度不合格时，记录实际渲染背景、前景、比值和阈值，再调整亮度并重新测量。

### 排版

- 默认字体使用 `Inter, ui-sans-serif, system-ui, sans-serif`；字重与用途使用规范令牌，不在组件内随意加粗。
- 正文优先使用 14px/20px 或 16px/24px；辅助信息使用 12px/16px；按钮标签至少保持清晰的 14px/20px。
- 展示型标题必须限制文本宽度并核对换行、字距和上下节奏。
- 长文本使用合理的 `max-inline-size`，不能靠固定高度或负字距掩盖字体加载和内容增长问题。
- 只加载实际使用的字体格式、字重和样式；不要用浏览器合成粗体或斜体代替缺失字重。
- 使用少量有语义名称的字号、字重和行高；标题层级必须递减，不能只靠视觉大小表达结构。
- 行高按角色设置：展示标题紧凑，正文舒适，控件标签与控件高度协调；字号越小，行高越不能过度压缩。
- 字号越大，字距越应谨慎；不要用统一的负字距覆盖所有文本。
- 截断只用于确实需要单行摘要的场景，必须提供完整内容的可访问方式；正文、错误和按钮标签不能被静默截断。
- 文案使用自然语言和项目既有语气，CSS 负责视觉大小；按钮文案使用动词开头，链接描述目标，不用“点击这里”。
- 数值变化的表格、计数器和状态指标使用等宽数字；多语言文本遵循语言方向和双向文本规则。
- 移动端输入字号不得小于 16px，避免浏览器自动放大。

### 布局与响应式

- 组内间距优先使用 4px/8px 节奏，区块间距从 16px、24px、48px 等层级选择；同一层级不能混用近似值。
- 相关内容必须通过 DOM 顺序、Grid、Flex 或逻辑属性表达关系；禁止为匹配单张截图使用脆弱的绝对坐标。
- 优先使用 `block-size`、`inline-size`、`margin-inline`、`padding-block` 等逻辑属性，保证 RTL 和本地化可用。
- 组件必须容纳更长标签、翻译文本、键盘焦点和错误信息，不能依赖 `white-space: nowrap` 隐藏真实内容。
- 页面在 320px 宽度和 200% 缩放下仍应保持可操作，不得因固定宽度造成横向滚动或内容遮挡。
- 用空间表达分组关系，分隔线只用于确实需要的层级边界；控件与说明内容必须保持清晰区分。
- 重复区域对齐到共享边缘；顺序按重要性组织，隐藏内容必须有可见的展开线索。
- 交互目标之间保留足够的呼吸空间，按钮不要贴住容器边缘；内容可以延伸到边缘时，控件仍需保留安全内缩。
- 优先保持结构关系，直到真实内容增长导致断点；断点应由内容需要触发，而不是由单张截图的宽度触发。

### 可访问性与交互

- 能使用原生 `button`、`a`、`input` 的地方必须使用原生元素，再通过样式实现视觉效果。
- 原生元素已有的事件必须直接使用原生事件名并透传原生事件对象，例如 `click`、`input`、`change`、`focus` 和 `blur`；禁止为它们创建仅改名的包装事件。
- 只有原生事件无法表达的组件语义或额外结构化数据，才允许使用自定义事件；自定义事件名称必须描述组件语义，不能使用 `e-` 前缀伪装成框架事件。
- 可交互元素必须有可见的 `:focus-visible` 状态；焦点环至少 2px，并与相邻表面有清晰区分。
- 触控目标默认至少 44×44px；视觉尺寸较小时用透明内边距扩展命中区域。
- 键盘操作必须覆盖组件实际需要的 Enter、Space、Tab、方向键和 Escape 行为。
- 禁用、加载、错误和选中状态必须同时更新语义属性与视觉表现；加载时避免重复触发操作。
- 图标通过 `currentColor` 继承语义颜色；装饰性图标隐藏于辅助技术，信息性图标提供可访问名称。
- 尊重 `prefers-reduced-motion: reduce`，减少或取消非必要位移、缩放和循环动画。
- 表单控件必须有真实标签；占位符只能展示示例，不能替代标签。错误信息靠近出错控件并说明修复方式。
- 模态层打开时将背景设为不可交互，焦点进入模态层；关闭后恢复到触发控件，并限制背景滚动。
- 动态结果使用稳定的状态播报区域；普通更新使用 polite，紧急错误才使用 alert。
- 图片按用途提供空、信息性或功能性替代文本；装饰内容不能污染辅助技术阅读顺序。
- 页面保持一个主内容区域和连续的标题层级；重复导航前提供跳过链接，锚点标题保留顶部滚动偏移。

### 表面、细节与动效

- 内层圆角不得大于外层圆角；嵌套表面遵循同心圆角关系，避免视觉溢出。
- 边框、阴影和背景必须来自表面语义令牌，不通过额外玻璃模糊制造未经设计的层次。
- 状态过渡默认使用 150ms 和 `cubic-bezier(0.2, 0, 0, 1)`；按压反馈可使用 `scale(0.96)`，并受减少动效设置约束。
- 悬停不应只改变颜色；必要时结合边框、阴影或轻微位移，同时保持布局稳定。
- 图标尺寸、基线、间距和视觉重量必须与文本一起核对，不能用相似占位图标替代真实资源。
- 动画必须可中断，进入动画只在页面加载完成后触发；退出动画保持克制，并避免阻塞用户下一步操作。
- 多元素进入时使用有限的分组和错峰，不能让内容逐个缓慢出现；主题切换时抑制过渡闪烁。
- 只对实际变化的属性做过渡，谨慎使用 `will-change`；不为静态页面预先保留合成层。
- 同一 SVG 通过 `currentColor` 表达不同状态，图标描边重量应与相邻文字重量匹配。
- 图片容器需要与表面边界一致的轮廓；装饰性光晕不能扩大交互命中区域。

## 组件审查流程

1. 明确组件职责、语义、状态和内容增长范围。
2. 建立或复用基础色阶、语义令牌和组件别名，先确定 Light/Dark 两套值。
3. 先实现结构和原生交互，再实现令牌驱动的视觉层。
4. 逐项核对默认、悬停、聚焦、按下、禁用、加载、错误、选中和危险状态。
5. 用实际内容检查长文本、窄屏、键盘、RTL 和 200% 缩放。
6. 计算实际渲染对比度并记录无法验证的项目；浏览器截图逐项对比外部参考。
7. 只有在结构、令牌、可访问性和视觉状态都通过后，才补充文档示例。

## 实现验收

每个 EOS 新组件完成前必须满足：

- [ ] Light/Dark 两套主题均有对应实现
- [ ] 所有颜色来自语义令牌
- [ ] 字体、字号、行高、字重与 Figma 对齐
- [ ] 尺寸、间距、圆角、边框和阴影与 Figma 对齐
- [ ] 默认、悬停、聚焦、禁用、加载、危险等状态已核对
- [ ] 图标使用真实资源或已确认一致的项目图标
- [ ] 通过实际浏览器截图逐项对比，而不是只通过编译
